# 项目约定与功能需求

这里保存两车的硬件需求、开发约定、模块边界和验收顺序。项目入口见 [根目录 README](../README.md)，工作包认领见 [多人开发分工](TEAM_DEVELOPMENT.md)，当前遥控与接口状态见 [遥控与任务说明](PERIPHERALS_AND_TASKS.md)。

## 1. 已确定的项目约束

比赛规则已加入资料目录；规则参数、裁判模块接线、版本疑点及下一轮工作见 `RULES_REQUIREMENTS.md`。当前每车一块 C 板的约定不变，裁判系统主控模块单列。

框架阶段整改：框架复核的四项逻辑问题已修复，两车重新编译及主机回归验证通过，详见 `archive/FRAMEWORK_FIXES.md`。本轮 IMU 移植与复核见 `PERIPHERALS_AND_TASKS.md`。

1. 工程车与炮台车是两个独立工程，各自独立编译、调试和烧录。
2. 每辆车只有一块 C 板，独立负责本车底盘及上层机构。
3. 两车底盘设计相同，公共模块直接分别放在各自工程内。不得建立跨工程源码依赖、外部公共库或共享 Common 目录。
4. 公共模块的接口、逻辑和修复须同步维护；车辆差异集中在本车配置和专有模块中。
5. 沿用已有 STM32CubeMX、HAL、FreeRTOS、CMake/Ninja 与 C/C++ 工程。保留现有目录和项目名，避免无必要的重构。
6. 未确定的硬件映射、机构参数和控制参数必须注明待定。编译通过不能作为参数正确或上车可用的证据。

## 4. 规划的模块与目录

下面是当前各车工程目录规划（已按此落地）；历史文件清单见 `archive/FRAMEWORK.md` 与 `archive/DEEPSEEK_HANDOFF_RESULT.md`。

```text
每个车辆工程/
├── Core/                     # CubeMX 生成的入口与外设配置
├── Bsp/                      # CAN、后续 UART/SPI 等板级适配
├── User_Driver/
│   ├── Motor_Driver/         # 保留既有电机驱动，后续补达妙适配
│   ├── Remote/               # 遥控数据解析接口
│   └── IMU/                  # 姿态采集/解算适配接口
├── App/
│   ├── Common/               # 本工程自己的类型、状态和模块接口
│   ├── Remote/               # 输入规范化与模式映射
│   ├── Chassis/              # 履带运动目标
│   ├── Lift/                 # 前后抬升目标与同步约束
│   ├── Power/                # 功率/输出预算接口
│   ├── Protection/           # 故障、失联、使能条件
│   ├── Attitude/             # IMU 姿态接口（快照/超时；采集在 User_Driver/IMU）
│   ├── Motor/                # 本车设备注册与唯一输出提交入口
│   ├── Vehicle/              # 本车专有模块接入层（Task 只依赖这一层）
│   └── 本车专有模块/          # 工程车 Arm；炮台车 Gimbal、Shooting
├── Task/                     # 启动与周期调度，不堆积业务控制算法
├── Config/                   # 本车硬件映射与参数有效性标记
└── README.md
```

`App/Common/` 只是各车内部的同名目录，不能包含另一个工程的文件。具体模块与职责如下：

| 模块 | 输入 | 输出/职责 | 不应直接承担 |
| --- | --- | --- | --- |
| Remote | 归一化逻辑输入（[-1,1]）、时间戳 | 一致快照、在线状态、逻辑档位与使能/复位请求 | 直接驱动电机、绑定物理协议或通道 |
| Chassis | 行进与转向请求 | 左右履带目标 | 机械臂、云台动作 |
| Lift | 抬升请求、机构反馈 | 前后抬升目标与约束状态 | 未标定的自动越障 |
| Arm | 关节/末端请求、反馈 | 五关节目标、任务状态 | 编造连杆和逆解结果 |
| Gimbal | 角度/速度请求、反馈 | Yaw/Pitch 目标 | 拨弹时序 |
| Shooting | 发射请求、反馈 | 摩擦轮和拨弹目标、卡弹状态 | 绕过发射条件直接输出 |
| Power | 输出请求、可用功率数据 | 限幅后的预算 | 伪造可用功率或裁判系统数据 |
| Protection | 配置状态、设备健康、操作请求 | 允许运行状态、故障原因 | 各模块各自独立解除故障 |
| Motor | 经仲裁的整车目标 | 每个电机每周期唯一指令、设备反馈快照 | 接收多个模块相互覆盖的直接写入 |
| Task | 模块接口 | 固定顺序调度与启动管理 | 重复实现驱动或控制算法 |

初期保留已有 CAN 发送和 DJI 服务任务，增加一个应用启动入口与一个周期控制任务即可；当前已是五个任务（含 2 ms `App_Control` 与 2 ms `IMU_Acquire`），不要再为每个目录创建任务。

## 5. 数据与调度约定

建议周期数据流为：读取一致反馈快照 → 判断设备健康和操作模式 → 生成本车各机构目标 → 应用功率及故障约束 → 唯一提交电机输出。驱动更新反馈，应用模块通过接口读取，不直接访问其他模块的可写全局变量。

接口须明确单位、方向、范围、有效状态及更新时间：

- 应用层角度采用 rad，角速度采用 rad/s，长度采用 m，时间采用明确标注的 tick 或秒；IMU 温度用 °C，加热占空比用归一化 0..1。
- IMU 解算结果对外统一为 roll/pitch/yaw（rad）与三轴角速度（rad/s），快照带有效性和毫秒时间戳；驱动原始 LSB、DPS、g 只在 `User_Driver/IMU` 内换算，默认输出板上传感器坐标，车体安装矩阵未核验前不能当作车体姿态。
- 遥控原始值先归一化；调试通道编号、正方向和开关编码在配置表中说明。
- 现有驱动的速度设定为归一化值，反馈为转子 rpm，位置为转子圈数；转换在适配层完成。关节输出角度还需减速比与零位信息。
- 不得把现有 GM6020 变量名中的 `current` 直接作为实际安培值使用；物理意义须对照型号手册核验。
- 反馈快照包含有效性、时间戳与健康状态；跨中断和任务读取时保持一致，避免读到半更新数据。
- 无法执行、未配置和未实现必须返回可区分的状态，不得把默认零值当成有效测量或成功完成。

C 文件调用 C++ 应用时提供纯 C 可见的入口头文件，并用 `extern "C"` 处理链接。CubeMX 生成文件中的手动接入放入 `USER CODE` 区；库和业务源文件分别管理。

## 6. 启动、模式与停机

首轮框架上电默认处于未使能状态：配置未确认、遥控未接入或设备未就绪时，保持无动作输出，不自动创建会等待硬件反馈的电机对象，不自动完成校准或动作。

启动须先建立 RTOS 对象和必要资源，再注册设备和接收路径；中断回调只能访问已经就绪的数据与 RTOS 对象。初始化采用有限时间或分阶段检查，离线设备不能使其他模块永远停在构造函数中。

后续至少需要表达未就绪、待使能、运行与故障状态，并明确失联、模式切换和故障后的输出策略。空闲时必须清除旧的运动请求，避免既有发送缓存继续保持上个周期命令。抬升及机械臂受重力影响，实车故障策略须结合机械自锁/制动条件确定，不能把“位置设为 0”当作停机。

遥控接入：USART3 + DMA/IDLE 每帧保存 18 字节 DBUS 数据与帧到达时刻，控制任务解析通道/开关/键盘并用到达时刻判 42 ms 失联（延迟处理的过期帧直接丢弃）。左 S1 三档决定路由：中档 `APP_MODE_CHASSIS` 走公共底盘，上档、下档分别进入各车 `app_vehicle_on_up()` / `app_vehicle_on_down()`（具体动作由各车负责人填写，不预设手动/自动）。右 S2 采用简单电平使能：上档请求使能，中/下档停用，下档同时产生复位请求；不复用旧工程“下档回中后上档”的重连资格序列。各车上下档入口可通过 `app_remote_get_aux_snapshot()` 读取四通道、S1/S2、鼠标、键盘（带有效性与到达时间戳，失联/非法帧后清零）。物理映射初始值需上板核验，不假设跨车遥控或车间通信。详见 `PERIPHERALS_AND_TASKS.md`。

IMU 接入：USART/SPI 等外设初始化完成后，独立 `IMU_Acquire` 任务负责 BMI088 初始化、2 ms 采样、温度准备、静止零偏校准和 EKF 解算；初始化等待通过 `osDelay` 让出 CPU，不阻塞 `App_Control`。状态流程为 INIT → TEMP_PREP（有效温度后才允许加热，达到目标附近并持续稳定）→ CALIBRATING（静止 500 样本）→ RUNNING；故障后立即停热并撤销姿态，500 ms 后重走准备流程。校准完成前不发布有效姿态；超过 20 ms 无新姿态时 `app_attitude_update()` 撤销旧快照。温控使用 PF6/TIM10_CH1 1 kHz PWM，上电默认关闭，过温、升温异常、温度过期、传感器错误或任务停更都会关热；`App_Control` 的加热看门狗在 IMU 任务停更 300 ms 后强制占空比归零。车体安装方向矩阵默认单位阵且 `vehicle_mounting_verified=false`，上板前不得声称姿态已在车体坐标系验证。

## 7. 配置表与待确认事项

每车需维护完整设备表：逻辑名称、型号、CAN 总线、实际电机 ID、收发报文 ID、控制模式、方向、减速比、零位、限位和确认状态。现阶段总线与电机 ID 均待定；占位项必须有独立的 `configured=false` 等有效性标记，未确认时禁止参与设备注册。

优先待确认：

1. 各电机 CAN 分配及实际 ID；组合帧共用字节槽、反馈 ID 和达妙报文的冲突检查。
2. DR16 DBUS 接收已接入（USART3 + DMA/IDLE）；通道/开关映射、42 ms 失联门限为初始值，待上板核验接收电平、实际帧周期、四轴方向与 S1/S2 字段。
3. 履带尺寸、减速比、最大速度；抬升行程、同步关系、限位与支撑条件。
4. 机械臂坐标系、连杆尺寸、零位、限位、末端姿态要求与逆解可达条件。
5. 云台机械限位、摩擦轮目标、拨弹定量方式和防卡弹条件。
6. IMU 安装方向及用途、安装矩阵、零偏校准效果与任务时序；PF6/TIM10 加热器的目标温度、功率/热惯性、PWM 极性、温控 PID 与保护阈值；功率信息来源、功率限制和整车使能条件。

这些信息不妨碍无动作框架的搭建，但对应功能在确认前不得声称可用。

## 9. 构建与验收顺序

在任一车辆工程目录中，工具链已加入 PATH 时：

```powershell
cmake --preset Debug
cmake --build --preset Debug
```

当前两车的 CMake 项目名均为 `dx_assignment5_freertos`，输出 ELF 同名但位于各自构建目录，烧录时需核对来源。最新构建与回归结果见 `PERIPHERALS_AND_TASKS.md`；历史记录见 `archive/`，`archive/BASELINE_REVIEW.md` 是首轮基线历史记录。

开发按以下阶段验收：

1. **框架阶段**：两车独立编译、模块接口与配置门控齐全；无硬件时保持未使能，所有未实现项可见。
2. **通信阶段**：核验接线与报文，先单设备、再多设备；确认初始化超时和失联报告。
3. **机构阶段**：低幅度单电机验证方向和反馈，再验证各机构控制；先标定零位与限位。
4. **整车阶段**：分别验证底盘、抬升、机械臂或云台发射系统，再进行车辆协作。

框架、既有逻辑修复、三档分派、基础遥控接入与 BMI088/姿态/温控移植已完成；当前从通信、IMU/加热器上板核验与硬件标定推进后续阶段。基线能编译不代表通信、控制闭环或实车功能已经完成。
