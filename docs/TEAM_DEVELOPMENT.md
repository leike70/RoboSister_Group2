# 两车多人开发与任务分工

更新：2026-11-10。本文用于分发开发任务；负责人姓名待认领，同一人可以兼任多个工作包。

## 1. 先明确怎么分

按功能模块分工，每个实现文件同时只有一位主要维护人。上档、下档是整车操作入口，不是两份包办所有功能的大程序；入口调用各负责人开发的模块。

两车各一块 C 板、各有独立工程。公共模块在各车工程内分别保存，由公共模块负责人同步维护，不建立共享库或跨车源码依赖。

当前已具备基础遥控接收、解析、在线/失联判断及三档分派；按键与原始开关快照已提供。BMI088 六轴 IMU、四元数 EKF 与 PF6/TIM10 温控已接入（SPI1 轮询、独立 IMU_Acquire 任务、温度准备、静止校准、20 ms 姿态超时），C5 转入上板标定与维护阶段。上下档具体动作仍为空，电机硬件适配、机构参数和控制算法仍待实现。以下工作包是后续任务，不表示功能已完成；当前技术状态见 [遥控与任务说明](PERIPHERALS_AND_TASKS.md)。

文中的路径以车辆工程为起点：

- 工程车：`project file/Engineering robots/`。
- 炮台车：`project file/Turret Robot/`。
- 标注“两车”的工作包，修改两边对应文件；只有机构配置值允许按车不同。

## 3. 哪些文件统一整合

“统一整合”表示由指定维护人应用已讨论好的改动，不要求每次普通实现都找用户批准。

| 文件或区域 | 整合方式 |
| --- | --- |
| 两车 `Task/app_task.c`、`Core/Src/freertos.c` | I0维护启动、周期和任务创建。模块负责人提交所需调用位置/周期，不各自添加线程或改调度 |
| 各车 `App/Vehicle/app_vehicle.c` | E0/T0分别维护；其他成员实现自己的模块并提供调用说明 |
| 各车 `Config/app_config.c` | I0或指定本车配置维护人合并；每个模块提交自己字段的数值、单位、来源和验证情况，避免整文件覆盖 |
| `Config/app_config.h`、`Common/app_types.h`、跨模块公共头文件 | 接口提供者与调用者先对齐签名、单位和失败语义，再由维护人同步两车及调用方 |
| `.ioc`、`Core/`外设初始化与中断、CMake文件 | C3/C4/C5/C6提出外设资源需求，I0协调后合并；C5已占用 SPI1(PB3/PB4/PA7)+CS(PA4/PB0)+PF6/TIM10_CH1(加热 PWM)，改动前先对齐；不要各自生成一套CubeMX文件覆盖别人改动 |
| `tests/framework_regression.c`、`tests/imu_regression.c`、`tests/imu_bsp_regression.c`、`tests/CMakeLists.txt` | I0合并测试改动，保留原回归；多人测试可使用各自独立文件后接入 |
| 模块README | 模块负责人更新自己的接口、参数与验证状态；共享README的改动由该目录维护人汇总 |

`app_vehicle.h`是两车相同的公开接口，不能为了本车功能随意改成不同版本。`app_vehicle.c`允许因车辆不同而不同。

## 4. 接口与依赖：以现有头文件为起点

下表是现有接口，不代表底层功能已经具备。接口需要扩展时明确提出，不另外写一套同名职责的私有接口绕开框架。

| 工作包/使用者 | 已有输入或调用 | 已有输出或下游 | 开发前应对齐 |
| --- | --- | --- | --- |
| C1 底盘 | `app_chassis_update(request, now_ms)`；请求为m/s、rad/s | 经 `app_motor_request()` 提出左右履带角速度请求 | 轮径/轮距、方向、减速比、限速；停止与无效请求行为 |
| C2 抬升 | `app_lift_update(request, now_ms)`；前后目标rad | 两台6020位置请求及状态 | 零位/限位、同步关系、有效反馈、重力下支撑策略；遥控操作仍待分配 |
| C3 电机适配 | `app_motor_output_get()`读取最终命令 | 硬件驱动输出；`app_motor_feedback_get()`向应用提供机构侧反馈 | 型号/总线/ID、反馈更新时间、闭环实现位置、换算、输出停用行为 |
| C4 遥控 | 接收回调保存字节与到达时刻；任务解析并 `app_remote_publish_frame()` | `app_remote_get_snapshot()`、`app_remote_get_aux_snapshot()` | 保留中/上/下路由、基础按键状态与失联清理；不绑定机构动作 |

| C6 功率 | CAN 0x31 已有 `app_power_on_can_frame()`、`app_power_get_feedback()` 和 `app_power_get_policy()`；旧代理另由 `app_power_get_budget()` 提供 | 左右履带策略经 `app_motor_submit()` 输出 `current_limit_norm` | 核验 0x31 实际总线/周期/超时；与 C3 接通最终电流/力矩限制。旧归一化预算不能当真实功率 W |
| E1 关节 | `app_arm_set_joint_target()`、`app_arm_set_end_target()` | `app_arm_update()`、关节反馈、统一电机请求 | 五关节顺序、限位、反馈判定、E2求解调用位置 |
| E2 运动学 | `app_arm_kinematics_forward()` / `inverse()` | 位姿或关节角及返回状态 | 长度m、角度rad、基坐标、姿态定义、夹爪自由度如何处理、不可达判定 |
| E3 作业流程 | `app_arm_task_request()` / `cancel()` | `app_arm_task_get_state()`；通过E1接口设置目标 | 当前没有周期推进接口，需补充接口提案和接入点；不能在request里阻塞执行整段流程 |
| T1 云台 | `app_gimbal_set_target()` | `app_gimbal_update()`、反馈与统一电机请求 | rad/rad/s、Yaw/Pitch限位、PID/前馈所在层、6006协议适配 |
| T2 发射 | `app_shooting_update(request, now_ms)` | 摩擦轮/拨弹请求及发射/卡弹状态 | 摩擦轮就绪、拨弹定量、反馈判定、超时、防卡弹与恢复条件 |

跨模块约定：

- 应用角度rad、角速度rad/s、长度m、线速度m/s；时间字段明确为ms并使用同一基准。驱动rpm/转子圈数在适配层换算。
- 状态至少区分未配置、未就绪、未实现、离线、参数错误和故障；反馈的数值只有在有效且未超时时才能用于控制。
- `init`、`update`、`stop`不等待其他模块“直到成功”；耗时流程分周期推进，失效/取消要有明确出口。
- 同一电机的控制环只安排在已约定的一层，不能应用层与驱动层重复闭环；模块接口输出什么命令类型由C3与对应机构负责人共同写清。
- 应用模块只提请求，不直接发CAN、不私自实例化电机对象。每周期最终输出仍由 `app_motor_submit()`统一提交，硬件适配只消费其最终有效命令。
- 状态快照保持一致。当前主周期读取逻辑与原始遥控快照时，应在同一控制上下文使用；若新增独立任务读取并要求跨接口同帧一致，需约定组合读取方案，不能靠多次读取不同全局量拼帧。

## 5. 上下档怎样接多人开发的功能

当前调用关系：`App_Control → 在线/保护判断 → 清旧请求 → 中档底盘或本车Vehicle → 唯一电机提交`。
另有一个独立 `IMU_Acquire` 任务：BMI088 采样/温控/EKF 解算后只调用 `app_attitude_ingest()` 发布姿态；App_Control 每周期读取姿态快照并调用 `imu_heater_supervise()` 看门狗，IMU 任务不参与三档分派、不写电机请求。

| 档位 | 当前入口 | 谁改 | 内容边界 |
| --- | --- | --- | --- |
| 中档 | 公共 `Task/app_task.c` 调 `App/Chassis` | I0整合，C1实现底盘 | 当前仅有履带请求；抬升操作映射仍待约定 |
| 工程车上/下档 | 工程车 `app_vehicle_on_up()` / `on_down()` | E0 | 读取输入，选择/取消本车功能，调用E1/E3模块；E2算法放运动学文件 |
| 炮台车上/下档 | 炮台车 `app_vehicle_on_up()` / `on_down()` | T0 | 读取输入，组合云台/发射请求，调用T1/T2模块 |

上下档的具体含义和按键动作尚未分配，负责人认领后再填操作表，不默认上档手动、下档自动。每车操作表至少写：档位/按键、调用功能、触发方式（电平或按下边沿）、互斥关系、取消条件。

例如工程车可以由E1/E2/E3同时开发各自文件，再由E0把确定好的操作接入上下档；这个例子不预先指定哪个档位执行哪项任务。

各模块的周期调用点只能有一个：上层作业流程设置目标，底层机构模块在约定位置每周期更新一次，不能多个分支重复调用或争写同一电机。新增任务推进接口时，由E0/I0接入；当前空入口不会自动运行Arm/Gimbal/Shooting更新。

切换上下档、返回中档、失联、停用和保护拒绝输出时，继续清除旧目标、取消本车任务。模块新增内部状态后，其负责人补齐对应stop/cancel清理，不能只依赖外部清一次电机请求。

## 6. 公共代码如何同步

公共模块负责人一次交付两车对应文件及验证记录，I0检查接口和逻辑一致性。公共底盘、抬升、遥控、姿态、功率、保护、电机抽象、通用类型和调度逻辑按此维护。

配置值不做整文件复制：工程车和炮台车的设备角色、型号、总线、ID、零位、限位及规则参数分别保留在本车 `Config/app_config.c`。只合并实际涉及的字段，并记录来源和上板确认状态；未确认项继续无效。

公共补丁必须附“两车文件对应表”。确有车辆差异时写入本车配置或专有模块；无法同步时写明原因、当前影响和补齐负责人，不能默默形成两个版本。

## 7. 开发顺序与合并方法

1. **认领和接口对齐**：填写工作包、主要文件、所需输入、输出、单位和依赖。先对齐C3与机构模块、E1/E2/E3、T1/T2之间的接口，其他实现可并行开展。
2. **分别开发**：模块负责人维护自己文件，可使用明确标为测试用的输入/反馈开展算法和状态机验证；测试数据不能进入生产路径假装真实反馈。
3. **接口接入**：E0/T0整合本车动作入口，I0整合任务、配置和构建。不把所有业务实现塞进Vehicle或Task。
4. **两车构建和回归**：公共变更检查两车；保留现有遥控、失联、切档、快照和故障回归。新增算法/状态机按实际风险补充有意义的用例。
5. **按依赖上板验收**：先基础遥控与电机通信/反馈，再 IMU 静态校准与姿态轴向、PF6 加热器与温控保护，再单机构标定与控制，最后作业流程/整车联调。未完成依赖时可交付模块代码，但写清阻塞项和未测项。

没有统一代码仓库时，各成员在自己的完整项目副本开发，交付“修改文件/差异+说明”，由维护人合入主副本；不要多人编辑同一磁盘目录，也不要用一份旧的完整工程覆盖主副本。使用代码仓库时，各自分支开发，合并仍遵循上述文件维护和验收约定。仓库根 `.gitignore` 已排除 `work/`、构建输出、日志和个人 IDE 状态；提交前检查 `git status`，不要提交本机构建产物。

## 8. 每个工作包的验收要求

| 层次 | 交付证据 |
| --- | --- |
| 文件与接口 | 实际修改清单、头文件/调用说明、单位/坐标系、负责人；无跨车依赖 |
| 配置 | 必需字段、真实值来源、哪些已确认/未确认；不为演示而整体打开有效标记 |
| 纯逻辑 | 对适用模块提供正常、边界、无效输入和失败处理证据；流程模块还需取消、超时、失败与切档验证 |
| 构建 | 受影响车辆实际构建结果；公共变更构建两车；说明新增告警和既有告警 |
| 集成 | 调用点与周期明确；无重复目标来源、无独立CAN输出；失联/停用后状态可撤销 |
| 硬件 | 板卡/车辆、固件来源、参数、方向/反馈/限位与停用结果；未测写“未上板”，不能用编译通过替代 |

涉及输出的模块至少覆盖：未配置、无有效反馈、无请求、正常请求、失联/保护拒绝以及退出功能后的旧目标清除。机械臂/抬升的支撑或制动行为需与机械条件共同确认，不能把目标设零等同停止。
