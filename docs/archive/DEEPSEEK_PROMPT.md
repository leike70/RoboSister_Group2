# DeepSeek 首轮提示词：在现有两车工程中搭建框架

> 历史记录：本文保留对应阶段的事实与任务。当前开发从 [文档目录](../README.md) 开始；接口状态见 [当前遥控与任务说明](../PERIPHERALS_AND_TASKS.md)。旧文提到的根README详细章节已移到 [项目约定](../PROJECT_REQUIREMENTS.md)。

使用方式：将整个项目目录提供给能读取文件的 DeepSeek 开发环境，再发送下方提示词。若只能使用普通聊天，需同时提供根 README、本检查记录、两车 README，以及提示词要求读取的基础源码；只粘贴提示词不足以了解现有工程。

---

你是这个 STM32 机器人项目的框架开发者。请先读取项目根目录 `README.md`、`docs/archive/BASELINE_REVIEW.md` 和两个车辆工程内的 `README.md`，然后在现有工程上完成首轮框架搭建。README 是项目约束，不能用自行假设替换待定需求。

## 目标与硬约束

1. 保留两个独立工程：`project file/Engineering robots/` 与 `project file/Turret Robot/`。每车仅一块 C 板，独立编译、配置、烧录。
2. 两车公共代码各自放在本车工程，公共接口和逻辑同步；不得跨工程 include、链接源码、建立公共库或 Common 共享项目。
3. 沿用现有 `Core/`、`Bsp/`、`User_Driver/`、`Task/`、CMake/Ninja、HAL 和 CMSIS-RTOS V2。按根 README 增加 `App/`、`Config/` 等目录；不搬动已有驱动，不更换工具链。
4. 本轮交付能编译的模块骨架、状态与接口、配置有效性门控和实际任务入口。默认无动作输出；不生成声称已可上车使用的控制参数或完整控制算法。

## 第一步：先检查实际代码，再列改动清单

至少读取两车的 `CMakeLists.txt`、`CMakePresets.json`、`.ioc`、`Core/Src/main.c`、`Core/Src/freertos.c`、`Bsp/CAN_bsp.*`、`User_Driver/Motor_Driver/*` 及 `pid_driver.*`。

说明：已有 `project()` 已启用 C++，基线实际编译成功；不要仅凭 `enable_language(C ASM)` 判断 C++ 未启用。两车现有项目名相同，首轮保留。先记录输入基线与预期修改文件，再实施，不需要等人回复普通目录或命名选择。

若未获得上述文件，先列出缺失清单，只输出明确标为建议的方案，不能声称已修改项目或已编译成功。

## 第二步：建立模块与接口

公共模块：遥控输入与模式、履带底盘、前后抬升、姿态接口、功率预算接口、保护状态、设备注册及统一电机输出。

工程车：机械臂五关节接口、单关节调试入口、末端目标入口、运动学求解接口、抓取/搬运/倾倒任务状态接口。

炮台车：云台 Yaw/Pitch 接口、摩擦轮目标与反馈接口、拨弹请求和防卡弹状态接口。

为每个模块定义初始化、周期更新、目标设置、反馈/状态读取、停用/故障处理等必要接口。根据实际职责确定函数集合，避免制造一堆没有调用方的空函数。

建立一致的状态与数据类型，至少能区分：未配置、未就绪、正常、离线、未实现、参数非法和故障。所有占位实现显式返回未就绪或未实现，绝不把虚假的测量数据、IK 成功或动作完成传给调用者。

统一单位：应用角度 rad、角速度 rad/s、长度 m，时间参数名称写明单位；现有驱动归一化速度/转子 rpm/转子圈数在适配层换算。方向、减速比和零位来自本车配置，未知时禁止换算成伪造的机构反馈。

配置表覆盖每车 9 个逻辑电机。工程车：公共底盘 2×3508+2×6020，机械臂 2×4310+2×3508+1×2006。炮台车：同款公共底盘，云台 1×6020+1×6006，摩擦轮 2×3508，拨弹 1×2006。

电机总线、ID、控制模式、方向、减速比、零位、限位、PID、机构尺寸等未确认项要有独立有效标记。占位数值不能自动成为有效配置，不得因此构造真实电机对象或开始发送命令。不得让 DJI 驱动错误适配达妙 4310/6006。

遥控接口默认离线；IMU、功率和运动学接口默认未就绪或未实现。首轮无需移植完整遥控、达妙或 IMU 实现。模式中保留公共底盘与本车专有功能的逻辑入口，物理开关及通道映射待定；不假设存在跨车遥控或车间通信。

## 第三步：把框架接入实际启动和周期调度

保留已有 CAN1/CAN2 发送任务与 DJI 电机服务。增加必要的应用启动、周期控制入口，通过 C 兼容头文件及 `extern "C"` 接入 `freertos.c` 的 `USER CODE` 区，使用强弱符号时核对最终调用的实际函数。

初期只用一个整车周期控制任务调用各应用模块，不为每个模块创建任务。调度应覆盖：输入与反馈一致快照、健康/模式判断、机构目标生成、功率和保护约束、唯一电机输出提交。中断内不解算运动学或执行耗时动作，不阻塞等待其他模块。

上电、配置未确认、设备不在线时保持未使能。每周期只有一个入口提交各电机最终命令，模式切换和失联必须使旧请求失效。默认框架不使能电机；机械臂/抬升实车故障时的支撑或制动策略留为明确待办，不把位置归零当停止。

不要全局实例化会等待反馈的 `DJI_motor`，也不要在一个任务里无限等待未接入硬件而阻塞其他模块。硬件适配未完成时显式报告状态并继续维护应用健康信息。

## 第四步：正确接入 CMake

现有工程只递归收集 `Bsp/`、`User_Driver/`、`Task/`，新增 `App/` 源文件须纳入目标并提供实际使用的头文件路径。建议明确收集 `.c/.cpp` 和需要的汇编文件，不把 README、参考工程或生成输出误作源文件。

对含空格路径正确引用。保留现有 MCU、链接脚本、启动文件、HAL、FreeRTOS 及 C++ 工具链。C 入口头文件不能暴露 C++ 类或 C++ 专用语法。

## 第五步：处理已有驱动的接入问题

按 `docs/archive/BASELINE_REVIEW.md` 核对：构造函数无限等待、CAN 回调空指针/索引/帧长度、队列消息载荷生命周期、发送失败和信号量、初始化与中断顺序、组合帧冲突及旧输出残留。

首轮不要批量重写驱动。可通过不实例化硬件适配保持无动作框架；如果框架接入必须修改某处，单独说明依据、最小改动和验证，两车公共代码同步。不伪造 CAN2 FilterMatchIndex 的映射规则，不隐藏故障，不删除校准条件来假装初始化完成。

## 第六步：验证与交付

分别执行两车 Debug 配置与编译，报告实际命令、退出结果和 ELF 路径。若环境没有工具链，明确写“未编译”，不得用静态检查冒充编译通过。基线已有警告须与新增问题区分。

检查新增源文件确实被构建，应用入口确实被创建和调用；未配置时不会注册电机、使能输出或报告功能完成。对可独立运行的纯逻辑配置/模式检查做适量验证，无法在主机验证的板上行为明确登记，不能声称已上车测试。

每个新增模块提供简短 README，列明职责、接口与单位、调用顺序、配置、故障行为、调试步骤、负责人待认领及未实现项。更新两车 README 的真实状态，保留根 README 中的确定需求及待定项。

最终交付：

1. 实际修改文件清单和新增目录树。
2. 模块依赖、启动顺序、周期数据流及关键接口表。
3. 两车构建结果、已存在与新增警告。
4. 公共模块同步情况及本车配置差异。
5. 已实现/仅骨架/未实现清单，待确认硬件参数和下一轮调试顺序。

请现在开始读取文件、列清单并搭建首轮框架。不要把计划、伪代码或孤立的示例片段当成已完成的工程修改。
